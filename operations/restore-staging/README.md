# Physical backup conversion staging

The Terraform root in `terraform/` combines the temporary version-bound access component and a separate x86 conversion host. Its backend is a distinct key under Dev, `dev/restore-staging.tfstate`, in the existing protected state bucket. Permanent Dev CI has no state access or administration over this root. Persistent resources remain in IaC. Provisioning defaults off; no existing Dev/shared root enables it.

Before planning an enabled root, reconcile ownership of all proposed IAM names and the SG, verify the current AMI/VPC/subnet, validate source selection and exact key/VersionId policy documents, confirm the existing Dev destination/host, current credit coverage, 160 GiB / max48h approval and peak quota. An ARM builder must not run concurrently. Bind all private inputs, source manifest, code, backend, lockfile, fixed lease and full saved plan to the review. Approval of capacity alone is not approval of an arbitrary plan. `restore_preflight` is review metadata, not a substitute for these proofs; do not populate it merely to make Terraform pass.

No source data, passphrase, payload secret or business row belongs in Terraform or public logs. A reviewed private cipher transfer and a pinned pgBackRest/PostgreSQL toolchain are prerequisites. Bootstrap only installs OS tools and sets a persistent absolute stop timer. It does not start PostgreSQL, export data, fetch a cipher or copy the source. Host, disk and SG use the temporary `env=restore` tag, outside CI's env=dev write scope; record temporary costs against the account-wide gross budget and approved envelope until cost attribution is explicitly reconciled.

The copied repository must be read-only. Use the fixed pgBackRest set, validate file checksums and required WAL before physical recovery, and capture tool output privately. Version2.57.0's verify implementation returns rendered status without throwing for every verification result, and includes a TODO for final required-WAL reconciliation: exit0 alone does not establish valid backup data. Require a successful detailed report and an independent WAL coverage check. Never run stanza-create, expire, repair or write against the legacy repository.

Use empty PGDATA and a network-isolated compatible container, disable preloads/replication/schedulers and business writers, inspect sensitive-data/schema/extension/collation requirements, then build the same-snapshot manifest and reviewed logical export. Own Dev credentials and targeted data treatment precede import into the empty Dev database. Measure the logical target and backup/proof workspace before import; the existing Dev disk limit must not be enlarged or data deleted silently.

Fixed lease expiry denies S3 independently and stops compute while preserving data on the stopped host. Storage charges continue. After the real Dev restore, own backup and independent recovery are proven, prepare a cleanup plan listing the instance and root volume ID, profile, policies and owned temporary artifacts. A reviewed termination deletes this temporary root volume; it must not occur before those gates. Expiry never auto-terminates, deletes backups, changes the source bucket or destroys permanent Dev resources. Preserve private evidence and the protected state.

This root is preparation only. Actual access/negative tests, current lease, timer/reboot behavior, egress isolation, payload/WAL integrity, compatibility, data reconciliation and cleanup remain runtime evidence requirements.

The dedicated [security gate](../../docs/restore-staging-security-review.md) scans this root with an explicitly synthetic, expired scanner fixture. Only two source-bound, dated exceptions are accepted; it never grants permission to provision or substitutes runtime verification.

## Version-pinned transfer

`copy-selected-source.py` is an operational transport for the approved Linux staging host, not a provisioning or database-restore script. AWS Core must first verify the actual instance/profile, encrypted volume, available capacity and lease against the reviewed plan. Deliver the exact frozen private source manifest and script by the reviewed private executor; do not regenerate a latest selection. Run only after the staging and source-access gates have passed:

```bash
python3 /opt/chico-restore/copy-selected-source.py \
  --manifest /run/chico-restore/source-selection.json \
  --manifest-sha256 "$REVIEWED_SOURCE_SHA256" \
  --destination "/srv/chico-restore/$IMPORT_ID" \
  --not-before "$REVIEWED_LEASE_START" --expires-at "$REVIEWED_LEASE_END"
```

The transport refuses root/permanent Dev/foreign AWS identities and requires `chico-dev-restore`. Its only AWS APIs are STS identity and versioned S3 GetObject; it never lists latest, writes the source, restores archived objects or syncs a repository. It validates manifest hash, safe unique paths, selected versions, returned sizes/ETag/timestamps, local bytes and SHA256. ETag is compared only as metadata; it is never assumed to be SHA256. A returned FULL_OBJECT SHA256 is checked when present; absent/composite checksums remain explicitly unverified.

The [private cipher protocol](../../docs/restore-cipher-transfer.md) uses an ephemeral RSA3072 recipient under checked tmpfs and a context-bound OAEP/SHA256 envelope. Only the public key and nonsecret metadata can enter SSM output. The operator's private controller must authenticate that key's actual SSM origin before sealing; a key file or synthetic test alone is insufficient.

It requires a fresh private directory and copy workspace; failures preserve partial files with a failure record and no completion marker. No automatic cleanup, resume, disk expansion or data deletion occurs. A successful transfer freezes local hashes and read-only permissions, then writes a private completion record. It explicitly leaves backup/WAL integrity and database restore unproven. Bind only the `repo/` child read-only into the isolated pinned toolchain; the private parent stays0700 and cipher configuration is a separate protected tmpfs mount. File permissions alone are not an immutable mount.

## Runtime package prepared after the partial Dev apply

This is an offline procedure, not approval to provision, access the source, extend a lease or restore data. The coordinator keeps AWS/SSM/state/merge mutations serialized. Stage creation still requires the updated PR, complete saved plan, exact financial/capacity review, source-access policies and human gates. Dev convergence and synthetic backup/recovery precede the real copy.

The staging bootstrap uses AL2023 `curl-minimal` and `awscli-2`, verifies CLIv2, and still enables its absolute persistent stop timer **before** package installation. A failed bootstrap does not authorize replacing a populated staging host. Neither expiry nor shutdown removes EBS charges. `modules/restore-staging/main.tf`, IAM and the two existing source-bound security exceptions are unchanged; the reviewed bootstrap hash is recorded separately from the Terraform-source hash. Security scanning, mock tests and timer/reboot evidence remain required.

### Transfer and cipher/configuration gates

1. Renew the account/host/profile/lease, source-manifest SHA, destination controls, quota and capacity privately. Fix a fresh import ID and all178 source versions from the existing selection; no latest re-selection, new export or source-bucket modification. State staging remains separate. Verify the absolute timer and IAM expiry agree; preserve enough of the approved window for recovery and reviewed cleanup.
2. Install the reviewed scripts root-owned with their approved hashes; deliver only nonsecret metadata through SSM. Run version-bound copy under `chico-dev-restore`, with no root/runtime substitute. Inspect completion evidence privately, pin its SHA256 and verify all object hashes locally before consuming the repository. A transfer-complete marker does not establish pgBackRest/WAL integrity. Failure preserves only its own partial workspace; no blind resume, wildcard deletion or disk growth.
3. Use the authenticated RSA3072 recipient and envelope protocol. Download only the reviewed ciphertext/metadata VersionIds into the matching private import tmpfs. `open` produces root-owned `repo.pass`0600. Do not print its contents, hash or length. Reboot requires a new authenticated recipient and reissued envelope; never preserve the private key/passphrase on EBS.
4. Store envelope metadata as `/run/chico-restore/IMPORT_ID/envelope.json`0600. After private review, prepare the consumer configuration with the exact transfer-record and envelope hashes:

```text
python3 /opt/chico-restore/prepare-private-config.py --directory /run/chico-restore/IMPORT_ID --metadata /run/chico-restore/IMPORT_ID/envelope.json --metadata-sha256 REVIEWED_METADATA_SHA256 --transfer-record /srv/chico-restore/IMPORT_ID/transfer-complete.json --transfer-sha256 REVIEWED_TRANSFER_SHA256 --source-manifest-sha256 REVIEWED_SOURCE_SHA256 --instance-id EXACT_STAGE_INSTANCE --image REVIEWED_TOOLCHAIN_DIGEST --uid VERIFIED_UID --gid VERIFIED_GID
```

The helper validates pinned metadata/transfer, account/region/source/instance/import/recipient/lease, positive nonroot UID/GID and image digest. It consumes the private passfile inside the process and creates `pgbackrest.conf`0600 with the verified image owner. It refuses symlinks/hardlinks, overwrite, non-tmpfs, foreign or partial records and lease expiry. Source/key/pass files are never deleted. Expiry during generation removes only this invocation's new config. No plaintext enters argv/environment/stdout; no config/passphrase hash is emitted. Config creation is not proof that the passphrase decrypts the selected repository. The isolated verification must establish that separately.

For pgBackRest2.57 INI parsing, values are literal after the first `=` and surrounding whitespace is trimmed. This helper preserves supported UTF8 bytes unchanged, including `=`, `#`, quotes and backslashes; it refuses control bytes or boundary whitespace rather than silently rewriting the passphrase. Unsupported input is a concrete runtime limitation; do not trim, re-encode or rotate a legacy cipher by trial. Primary source: [ini.c at the pinned pgBackRest commit](https://github.com/pgbackrest/pgbackrest/blob/d9773a31c97077761ee8e7d06e073b0b0734e26f/src/common/ini.c).

Mount **only** that config file read-only at `/config`; do not mount its parent, which contains the private key/passfile. The repo mounts RO at `/repo`. Use the separately reviewed B1 isolated runner/digest with numeric nonroot UID, network none, read-only rootfs, all caps dropped, no-new-privileges and explicit tmpfs over the upstream VOLUME. Do not construct an ad hoc Docker command that creates an anonymous volume or uses the upstream auto-initdb entrypoint. Verify the full/diff reports and independent WAL/control coverage before the physical recovery. B1 code is a separate change and must be integrated/accepted before this package is run.

This B2 layout deliberately mounts a **file** at `/config`, so commands use `--config=/config`. B1's synthetic fixture may instead mount a directory at `/config` and use `/config/pgbackrest.conf`. Do not interchange those arguments or mount the B2 recipient directory to reproduce the fixture layout.

### Safe first startup of the recovered physical clone

Do not start PostgreSQL with restored configuration, even for an initial SQL inspection. `config_file` selects the primary file, but PG16 still reads `PGDATA/postgresql.auto.conf`, whose values override the primary configuration. Nested includes can expand the effective settings. Command-line settings can override file values, and client startup options handle per-session settings. See [PG16 configuration precedence](https://www.postgresql.org/docs/16/config-setting.html) and [file locations](https://www.postgresql.org/docs/16/runtime-config-file-locations.html).

pgBackRest2.57's recovery writer preserves existing `postgresql.auto.conf` content while updating recovery options; a successfully generated restore_command is therefore insufficient. Its writer also creates signal files according to recovery type. Inspect the [pinned recovery writer](https://github.com/pgbackrest/pgbackrest/blob/d9773a31c97077761ee8e7d06e073b0b0734e26f/src/command/restore/restore.c). The following operations affect only the newly recovered clone, never the immutable repo or Dev's live PGDATA:

1. Recover the fixed label into a fresh encrypted clone path with no PostgreSQL/application process running. Use the reviewed immediate target; do not use preserve/standby/latest or reuse a nonempty PGDATA. Before any start, record PG_VERSION, `pg_controldata` (matching PG16 binary) and system identifier privately. Confirm required libraries/collations and inspect symlinks/tablespaces against explicit mount mappings; stop on unexpected external paths. Never mount the original host or Docker socket to satisfy a recovered link.
2. In that stopped clone, prepare a fresh private audit directory outside PostgreSQL's configuration search path, within its reviewed clone/evidence scope. Preserve restored `postgresql.conf`, `pg_hba.conf`, `pg_ident.conf` and referenced include files privately, without printing them or copying them to public artifacts. Do not source/evaluate them. Refuse unexpected symlink/hardlink/config type. Preserve/move `postgresql.auto.conf`, `recovery.conf`, `standby.signal` and the generated `recovery.signal`, if present, into that audit directory by exact paths with no overwrite. Do not edit or delete `backup_label`, WAL, control or data files as part of this quarantine.
3. Create a new empty `postgresql.auto.conf`0600 owned by the verified PostgreSQL UID, and one empty `recovery.signal`0600. Assert `standby.signal` and `recovery.conf` are absent. Quarantine is mandatory even with an external config file; no startup marker is implied by generating templates. Do not automatically undo the quarantine onto a cluster that has started.
4. Prepare `/run/chico-restore/IMPORT_ID/control-settings.json`0600 from the **observed** PG16 control values, with exactly schema1, postgresMajor16, systemIdentifier string, sourceManifestSHA256 and settings: `max_connections`, `max_worker_processes`, `max_wal_senders`, `max_prepared_transactions`, `max_locks_per_transaction`. Review their memory/process budget and source recovery requirements. Do not lower them to force startup or silently increase the host. Reconcile slots and other compatibility requirements before startup; an unreconciled requirement blocks the clone.
5. Generate inert startup files, using the privately reviewed control-file SHA:

```text
python3 /opt/chico-restore/clone-startup-templates.py --directory /run/chico-restore/IMPORT_ID/clone --control-settings /run/chico-restore/IMPORT_ID/control-settings.json --control-sha256 REVIEWED_CONTROL_SHA256 --source-manifest-sha256 REVIEWED_SOURCE_SHA256 --uid VERIFIED_UID --gid VERIFIED_GID
```

The helper writes templates only; it never moves source config, creates cluster signals, touches PGDATA or starts PostgreSQL. Mount the generated clone directory RO at `/scripts/clone` through the reviewed isolated runtime; it contains no cipher. Mount the individual pgBackRest config separately at `/config`RO, the copy at `/repo`RO and the exclusive recovered PGDATA at `/pgdata`RW. Create private `/tmp/socket` and `/tmp/pgbackrest` inside container tmpfs with the matching nonroot UID.

6. Start the pinned PG16 binary with this exact argument structure through the reviewed runtime, without reading a restored shell script: `/usr/lib/postgresql/16/bin/postgres -D /pgdata -c config_file=/scripts/clone/postgresql.conf`. Capture stderr privately. The template has no includes, listens only on its private Unix socket, uses peer auth for OS/DB user postgres and rejects other users/hosts. It disables preloads, archiving callbacks/libraries, external recovery-end/cleanup hooks, streaming connection settings, logical replication workers and autovacuum. Its sole restore_command is a literal local pgBackRest `archive-get` under `/config`, with async disabled. It does not copy any shell command from the restored config.
7. Target immediate recovery on the backup's current timeline with action pause and hot_standby enabled. This intentionally leaves the initial clone in read-only recovery for inspection; no promotion or replay resume is automatic. `immediate` reaches the backup's first consistent endpoint, and pause allows validation before proceeding. Confirm the actual point/system ID and that target was reached; missing WAL, early termination or shutdown is failure. See [PG16 recovery targets](https://www.postgresql.org/docs/16/runtime-config-wal.html) and [hot standby constraints](https://www.postgresql.org/docs/16/hot-standby.html).
8. Before the first SQL session, use a clean client environment and `psql -X` via the local socket. The client options are fixed and nonsecret: `PGOPTIONS='-c session_preload_libraries= -c local_preload_libraries= -c search_path=pg_catalog -c default_transaction_read_only=on'`. This suppresses recovered per-role/database preload defaults for that session. Do not inherit PGHOST/service/password/options from the backup or operator shell. First queries are only qualified built-in catalog/recovery functions, for example `SELECT pg_catalog.pg_is_in_recovery(), pg_catalog.pg_is_wal_replay_paused();`. Keep results private/boolean; do not execute application-defined functions, views, triggers or jobs as discovery.

The generic templates have unit-level safety coverage, not proof that PG16 accepted them or that the real backup recovered. A synthetic Linux startup/recovery test with the pinned binary is still required before real use. PG16 removed `promote_trigger_file`; it is deliberately absent, rather than setting an obsolete GUC. See [PG16 compatibility changes](https://www.postgresql.org/docs/16/release-16.html).

An independent opt-in startup integration is prepared in `tests/restore-private-config-integration.py`. It uses the official PostgreSQL16 image index pinned at `sha256:472efd9a66f2b2f1a5aeb18b28de74332e6ef88c2b93a1a5d812fb6db67a5f60`, explicit linux/amd64, UID999, network none, read-only rootfs, caps dropped, tmpfs sockets/runtime and coverage of its inherited VOLUME. It has no B1 module/image dependency. The fresh synthetic cluster proves that auto.conf wins before quarantine, the templates bypass an unsafe primary include, and clean PGOPTIONS suppress unsafe synthetic role-default preloads. It uses no recovery.signal and leaves `physicalRecoveryValidated=false`; WAL/recovery still require the separate B1 gate and eventual real proof. Only its fixed summary/binary hash may be published; raw private runner/config/PGDATA are excluded.

```text
python tests/restore-private-config.test.py
CHICO_CLONE_INTEGRATION=true sudo --preserve-env=CHICO_CLONE_INTEGRATION python3 tests/restore-private-config-integration.py --evidence /fresh/absolute/synthetic-ci-directory
```

The integration refuses an existing evidence directory, never starts Docker Desktop and performs no AWS calls. It starts a disposable CI-only PostgreSQL container and synthetic role writes; it must not run against the real staging/import paths. The package's preparation on Windows ran unit/syntax checks only; a Linux CI run is still required before reporting this integration green.

After catalog/classification review, data treatment can require writes in a separate controlled clone phase. Prepare a concrete transition/backup plan before leaving paused recovery; do not call `pg_wal_replay_resume()` or promote as a convenient way to unblock SQL. External network remains none, writers disabled and source repo read-only. Logical export to Dev uses own operational roles and the same-snapshot manifest; real Dev backup plus independent second restore still gate cleanup.

### Lease, stop, cleanup and evidence

Record only nonsecret hashes of scripts/source/ciphertext/control metadata, pinned object versions, toolchain digest/UID, request IDs, lease, counts and booleans. Raw configs/repo.pass/recipient key, pgBackRest diagnostics, SQL/TOC/dumps and catalog results stay private. Do not publish a hash of plaintext cipher configuration. A config-ready/template-ready response leaves restore/integrity flags false.

Before expiry, stop the exact recovery process safely and preserve evidence/data; do not extend its lease/timer or start replacement capacity without review. Expiry/reboot clears tmpfs and stops access/compute but leaves encrypted EBS and potentially IPv4 residuals. Cleanup requires the real Dev import, own backup and independent recovery, then a concrete Terraform plan by exact staging instance/volume/profile/policies and owned import artifacts. Review retained state, evidence and costs first. Never delete versions from `chico-backup`, change its policies/lifecycle, destroy permanent Dev root or disable audit/KMS to clean up.
