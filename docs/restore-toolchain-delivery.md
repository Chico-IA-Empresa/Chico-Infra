# Delivery proposal: existing ECR toolchain artifact

This workflow adds a reviewed data-plane path to the existing private chico-workers ECR repository in sa-east-1. It creates no repository, IAM policy, capacity, staging host, database or Terraform state. Code publication is separate from permission to execute it: an actual dispatch still requires privately renewed financial/package/storage evidence and the mandatory infra-apply-dev human deployment gate. It does not install, pull on staging, or recover real data.

Pull requests and relevant main pushes run only credential-free native amd64 producer checks. A protected first-attempt main dispatch runs the same fresh build, encrypted synthetic full/diff/SQLXML/WAL/recovery harness and complete Trivy scan. Existing canonical toolchain files and its established CI are fingerprinted; new or changed inputs require review. No older image or scan is used as proof for fresh bytes. CRITICAL/HIGH/UNKNOWN findings, incomplete inventory, changed reviewed package/finding fingerprints, a different image ID/layer set or uncompressed image larger than the privately approved bound (at most1GiB) stop publication before OIDC.

The private minimal review uses the existing financial metadata contract, actual main SHA, source-input fingerprint, package/finding review fingerprints, fresh existing-repository inventory fingerprint and approved storage/cleanup references. It contains no credit balance, prices, recipient address, credentials, source database payload or secret value. Configure the exact JSON privately and pass its SHA256 only after the operator has completed the reviews; placeholders or test fixtures are not approvals. The account/region/role/repository are fixed. Changes to the repository image/tag inventory invalidate the review before another publication; tags include main SHA and run ID, and rerun attempts are refused.

The review also binds expected_run_number to the next run ordinal of this exact protected workflow file. Read the latest workflow run_number across all events/branches immediately before preparing the private review and reserve the next value for the intended dispatch. GitHub assigns a distinct ordinal to every new run; a rerun keeps the ordinal but has run_attempt greater than1 and is refused. A different workflow file is refused as well. If another queued check consumes the expected ordinal, preflight must fail before AWS; reconcile and prepare a new exact review, never loosen the binding. Repository inventory alone cannot consume an approval after a failed partial upload, so this workflow/run binding is required even when no image/tag was created.

The ci-build-dev role already has the required ECR build/read grants for this repository. Publication must verify its exact live STS session, existing IMMUTABLE/AES256/scan-on-push/BASIC controls and unused unique tag. Only after those checks does it request a login token via stdin, using a private temporary Docker config that is removed on exit. No token, raw build log, raw AWS response, state, plan or financial JSON enters artifacts. Native containers run before AWS credentials are configured and never receive those credentials.

The pushed registry manifest/config digest must identify the scanned local image. The exact digest's ECR scan must complete without CRITICAL/undefined findings or incomplete counts. Scan completion must follow publication (one-second timestamp granularity tolerance), be at most one hour old, and its vulnerability-source timestamp at most48hours old. The scan's noncritical findings remain visible and pending operational review. Staging/host pull, image promotion, source-data access and real restore remain false in receipts. A changed taxonomy or unsupported/stale scan blocks completion; do not add a scan exception or extra IAM grant to bypass it.

## Storage, failure and cleanup gates

One new artifact is proposed with a conservative maximum1GiB uncompressed bound; actual compressed registry bytes are recorded after publication. The operator must compare the whole existing repository inventory plus that allowance to the originally approved ECR capacity, envelope, operational horizon, credit eligibility and reserve. Do not assume coverage from the image's small size or the existence of credits. Tagged retention is NOT automatic: the current repository has no lifecycle policy. retention_until_utc is a privately approved review/manual-cleanup deadline within the financial review, not a resource TTL or billing stop. Name the cleanup owner and deadline in the private review, preserving the original horizon. This code neither deletes/untags images nor changes lifecycle.

The release requires at least25minutes before the earliest of the external financial release, credit-review expiry at UTC midnight and the approved storage-review deadline. Push and scan wait are each bounded to10minutes, and every AWS read checks the actual release deadline. Failures after OIDC/push can leave a consumed tag or partial uploads; retain the receipt and reconcile actual image/storage/scan status privately. The attempted authorization is consumed even if no tag appears. Never retry the same run, replace/delete a tag to get past an error, or dispatch another attempt using the old review. A new attempt needs fresh inventory, storage/residual assessment, private review and human deployment approval. Do not assert a failed scan or absent tag means zero residual cost.

The publishing role cannot inspect lifecycle or create cleanup policies; the operator must revalidate lifecycle/retention independently before the protected dispatch. The separate staging root currently has no ECR pull grant. Any proposed read-only pull permission, image delivery to a host, lease, capacity, source classification, cipher transfer, compatibility and real-data execution need their own concrete plan/review/gates. No DNS/TLS public or business workload is included.
