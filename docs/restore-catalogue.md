# Minimal source catalogue candidate

This is preparation for the first isolated sensitive-data inspection required by phase1 v1.1 §9.1. It does not restore, decrypt, connect to an operational source or grant permission to process data. Classification by the owner remains separate from processing and from column-specific treatment/export approval. The existing full database manifest is deliberately not used for this first inspection because its counts, sequence values and definition hashes exceed the initial scope.

`minimal_catalogue.py` contains fixed PG16 queries C1–C7, a recovery admission query and a bounded response/output policy. A caller supplies a separately approved, already connected session; the library neither resolves credentials nor provides an operational host adapter. The bundled session adapter accepts only the two socket paths of its disposable CI fixture. No real source execution command exists in this closure.

The transaction is REPEATABLE READ READ ONLY with pg_catalog search_path and bounded statement/lock/idle timeouts. Admission binds the exact reviewed database, system identifier, PG16 binary version, selected source-manifest SHA and query-plan SHA. Recovery must be active, read-only and actually paused. `pg_is_wal_replay_paused` alone reports a request; the separate pause-state function must return `paused`. The checks run before each catalogue query and after the final query. A primary, resumed/replaced cluster, changed plan or wrong target stops collection; no promotion or resume is performed.

The fixed catalogue scope is database locale/provider metadata and ICU-rule presence; extension names/versions; relation and column identifiers/types/flags; constraint relationships; index flags/key numbers; and aggregate indicators of executable/external/large-object metadata surfaces. Definitions, comments, user rows, statistics/histograms, role passwords, connection/options, default expressions and large-object contents are excluded. Identifiers and locale metadata remain private. The database list is cluster-wide; relation/column/surface coverage is only the one reviewed database. Empty results do not prove that another database or an unknown surface is safe.

The response transport must enforce the16MiB bound before accumulating bytes. Each catalogue result is parsed as exactly one JSON document with duplicate keys/NaN/unknown fields refused; a100,000-record bound fails rather than truncating. The session adapter only sends the fixed reviewed statements. Recovered names never become SQL or connection strings; unsupported connection-name syntax requires review. A new private output directory and exclusive0600 files are required, with no overwrite or automatic deletion of partial evidence. Only after all queries, a final admission check and confirmed rollback is the complete private manifest written. Caller-facing results contain booleans and a query count, not identifiers, data or private output hashes.

## Synthetic validation

The proposed workflow has contents:read only, no id-token/AWS credentials/SSM/source bucket/ECR publication. It builds the current native Noble image, records its complete scan and uses the established synthetic-startup zeroCRITICAL gate plus the exact fixed APT inventory. All other findings remain visible; this synthetic gate never approves operational delivery or sensitive-data use. The independent delivery gate still requires zeroHIGH and its reviewed package/finding fingerprints. This closure must not be used to bypass the PR35 delivery failure.

The native fixture creates fresh primary/standby clusters in one network-none, unprivileged, read-only-root container with nonroot UID999 and private tmpfs. It creates only synthetic records/defaults/comments/function/view bodies with a fixed canary, takes its own pg_basebackup through local sockets and pauses its own standby. The proof must show actual primary refusal, actual paused recovery acceptance, native SQL/schema validity and absence of that canary in the collected catalogue. No source backup is mounted. Only the fixed synthetic summary, package scan and scanner metadata are uploaded; raw catalogue, SQL and diagnostics stay outside the public artifact directory. This proof is still pending until Linux CI runs.

## Remaining operational gates

Before real use: independent code/native review, current approved image/scan/delivery, actual staging/lease/IAM/storage/capacity/compatibility and source-integrity proofs, reviewed source-session adapter and installation payload, exact query/perimeter/output/retention/operator approval for sensitive processing, and owner review of resulting private identifiers. The collector does not establish semantic classification, masking, credential replacement, safe writable transition, export/import equivalence or real backup recovery. Those requirements remain mandatory. Nothing changes the source manifest or its integrity/restored flags.

Sources used for the fixed metadata boundaries: [PG16 database catalogue](https://www.postgresql.org/docs/16/catalog-pg-database.html), [attributes](https://www.postgresql.org/docs/16/catalog-pg-attribute.html), [constraints](https://www.postgresql.org/docs/16/catalog-pg-constraint.html), [indexes](https://www.postgresql.org/docs/16/catalog-pg-index.html), [control-file information](https://www.postgresql.org/docs/16/functions-info.html#FUNCTIONS-CONTROLDATA) and [recovery state](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-RECOVERY-CONTROL).
